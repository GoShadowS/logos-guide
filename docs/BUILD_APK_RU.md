# Android-сборка, публикация и переход на новую версию

Здесь собраны фактическая Gradle-конфигурация, опубликованный статус, поведение клиента обновлений и пользовательские действия. Сверено 2026-10-12 по проверенному `origin/main` `394361783557c5e578ec05b6a20fe40541bcf436`, GitHub tags/Releases API, source tree тега `release`, workflow и локальному APK. Это статическая проверка исходников и метаданных; она не является локальной сборкой, криптографической проверкой APK-подписи или тестом на устройстве.

## Состояние версии: целевой план, Gradle и публикация

Это не опубликованный релиз; `versionCode` для него не подтверждён. Владелец выпускает APK вручную через Android Studio; изменение/merge исходников не является сборкой или публикацией. ## Целевые сборки и OpenDoors

`debug` задаёт `applicationIdSuffix = ".debug"`, `versionNameSuffix = "-debug"` и `OPEN_DOORS=false`. `release` задаёт `OPEN_DOORS=false`. В Gradle нет product flavors. Соответствующий workflow проверяет сгенерированные `BuildConfig` обоих вариантов, однако результат CI PR #27 относится к тому PR и не является сборкой в текущей рабочей копии.

`OPEN_DOORS=false` действует на **новые Debug- и Release-сборки из текущего исходника**. Оно не удаляет эту функцию из старого кода и не меняет уже созданные/опубликованные APK. Release из тега `release` и отслеживаемые APK не заменялись этим изменением.

## Планируемый переход с удалением старого приложения

> Чтобы установить новую `1.0.1-release`, нужно сначала удалить установленную старую версию приложения, затем установить новый APK.

Это инструкция **для планируемого перехода после фактической публикации официального APK**. Сейчас APK `1.0.1-release` не опубликован; не скачивайте вместо него старый asset `1.0.0-opendoors` или локальный `1.1.0-release`.

1. **До удаления обязательно экспортируйте JSON и проверьте файл.** В исходниках тега `release` и текущего `origin/main` экран «Избранное» содержит экспорт JSON с системным выбором документа и предлагаемым именем `logos-favorites.json`. В установленной старой версии используйте экспорт, выберите общую папку «Документы»/«Загрузки» или другое хранилище вне закрытых данных приложения и убедитесь через файловый менеджер, что JSON существует и открывается. Бинарный APK старого Release не скачан и UI на устройстве не запускался, поэтому наличие кнопки в установленной копии не подтверждено. Если экспорт недоступен или файл нельзя сохранить и проверить вне данных приложения, остановитесь: не удаляйте приложение до решения этой проблемы.
2. **Удалите старую версию приложения.** Это обязательный шаг для данного перехода. Удаление может стереть локальную базу Room (избранное, пользовательские категории/папки, историю и сохранённые маршруты), Preferences DataStore (настройки и часть пользовательского состояния), состояние updater и кэш. В манифесте `allowBackup=true`, но системное резервное копирование/восстановление для этого удаления и последующей установки не проверялось; не рассчитывайте на него как на способ переноса.
3. **После появления официального Release** установите именно APK `1.0.1-release` из опубликованного проекта. До публикации у этой версии нет URL для скачивания.
4. **Восстановите JSON**, только если код импортёра именно выпущенного APK проверен. Путь в совместимой версии: «Избранное» → кнопка импорта JSON → в системном выборе документов указать сохранённый `logos-favorites.json`. Текущий импортёр `origin/main` принимает `schemaVersion` 1–2; старый exporter в source tag `release` записывает schema 2. В нынешнем коде импорт добавляет отсутствующие данные/объединяет записи, а не восстанавливает настройки. Но APK `1.0.1` отсутствует, поэтому его конкретная совместимость и успешный перенос на устройстве **не подтверждены**.

JSON-экспорт включает категории/папки, избранные записи, историю маршрутов и сохранённые маршруты. В нём нет настроек интерфейса/позиционирования, состояния первого запуска, состояния автообновления, кэша и иных Preferences. Такие данные после удаления могут быть потеряны. Не обещайте их восстановление системным Android Backup.

## Встроенный updater: что именно происходит

Поведение ниже проверено по `AppUpdateViewModel`, `AppUpdateRepository`, `VersionComparison`, `NavigatorApp`, About UI, Android Manifest и ресурсам. Оно описывает исходный код текущего `origin/main`, а не опубликованный `1.0.1` APK.

### Проверка

- Создание `AppUpdateViewModel` при старте вызывает `checkForUpdates(force = false)`. Проверка пропускается, если с последней сохранённой попытки прошло менее 24 часов. Время хранится в `SharedPreferences` `app_update_state` (`last_check_at`). В About доступна ручная проверка с `force = true`, обходящая интервал.
- Запрос выполняется только к `GET https://api.github.com/repos/GoShadowS/logos-guide/releases/latest`. Клиент не перебирает все tags/releases. В запросе задан timeout соединения 15 секунд и чтения 20 секунд.
- Для обнаружения клиента берёт `tag_name`, снимает необязательный префикс `v` и сравнивает только числовые `major.minor.patch` части `versionName`. Суффиксы, например `-release`/`-opendoors`, не упорядочиваются. **`versionCode` не читается и не сравнивается.** Для равных числовых частей обновления нет.
- Сетевая/JSON-ошибка отображает «Не удалось проверить обновления» и записывает время попытки, поэтому следующая автоматическая проверка обычно ждёт 24 часа. Отмена запроса не записывает timestamp. Невалидная версия возвращает `null` без исключения; ViewModel обрабатывает это как отсутствие обновления и может показать «Установлена последняя версия».
- Это ограничение актуально сейчас: GitHub Latest metadata указывает тег `release`, а текущая функция принимает только числовой формат вроде `1.0.1-release`; tag `release` не разбирается. Следовательно, UI может сообщить «Установлена последняя версия», хотя сравнение версии фактически не состоялось. Это поведение подтверждено source-level, не runtime.

### Загрузка и установка

- Проверка не скачивает APK. Если числовой `versionName` распознан как более новый, приложение показывает пользователю версию и кнопку «Скачать». Запрос на скачивание запускается только после нажатия.
- Клиент выбирает asset с точным именем `logos-guide-<versionName>.apk`, принимает HTTPS URL только с `github.com/GoShadowS/logos-guide/releases/download/...`, требует ненулевой объявленный размер и ограничивает скачивание 250 MiB. Timeout чтения загрузки — 45 секунд. Файл временно записывается в `cacheDir/updates`; неудачная или непрошедшая проверки загрузка удаляется, оставшийся кэш чистится при следующем запуске.
- После загрузки проверяются APK-формат, `packageName`, `versionName` и то, что числовой `versionName` новее установленного. Клиент **не проверяет `versionCode`, сертификат подписи, SHA-256 или SLSA provenance**. Слово «проверен» в строке UI не означает проверку подписи/хэша. Неудачи HTTP, формата или идентичности показывают сообщение об ошибке загрузки.
- После нажатия «Скачать» ViewModel по завершении файла автоматически вызывает открытие системного установщика. Это не тихая установка: при необходимости Android открывает настройки разрешения «Установка неизвестных приложений» для источника; пользователь возвращается в приложение и нажимает «Установить». Package Installer показывает подтверждение и сам решает, допустимо ли обновление, в том числе по подписи и `versionCode`. Клиент не перехватывает и не объясняет системный отказ из-за подписи или downgrade.

### Может ли старая версия получить `1.0.1-release` автоматически?

Нет. Исходный код опубликованного тега `release` (`1.0.0-opendoors` / code 3) не содержит updater; такая установка не может самостоятельно выполнить проверку или загрузку и требует ручной установки по шагам выше. Сам бинарный APK этого тега не скачан/не запускался, поэтому это вывод по исходникам тега, не device-тест.

Кроме того, текущая конфигурация `origin/main` имеет `versionName=1.1.0-release`: при нынешнем сравнении по числовому `versionName` кандидат `1.0.1-release` оказался бы ниже `1.1.0-release` и не был бы предложен как обновление. Новая версия `1.0.1-release` не собрана, её `versionCode` неизвестен, а обновлённый клиент/канал не проверен. Не обещайте автоматическое получение этой версии из какой-либо существующей APK.

## Сборка и публикация — не updater в приложении

В текущем `.github/workflows/android-release.yml` публикация запускается push-тегом `v*`. Workflow устанавливает JDK 25 и Android SDK/Build Tools 37, собирает `testDebugUnitTest assembleRelease`, ищет APK по версии тега, проверяет `versionName` через `aapt dump badging`, вызывает `apksigner verify` и создаёт GitHub Release. Отдельная job загружает SLSA provenance. Workflow проверяет корректность APK-подписи, но не доказывает, что сертификат совпадает с сертификатом установленной пользователю копии; также он не проверяет монотонность `versionCode` относительно предыдущего релиза.

`.github/workflows/android.yml` также ожидает Release APK с именем `logos-guide-1.1.0-release.apk` и текущим `versionName`. Следовательно, до публикации целевого `1.0.1-release` владелец выпуска должен отдельно согласовать версию Gradle, versionCode, имя ожидаемого файла и release/CI-конфигурацию. Эти файлы, подпись, версия, APK и Release в этой документационной задаче не изменялись; новая APK-сборка и публикация не выполнялись.

## Локальные данные приложения

Пользовательские настройки хранятся в Preferences DataStore; Room database `logos_favorites.db` содержит избранное, пользовательские категории, историю и сохранённые маршруты. Текущая Room-схема — версия 2; миграция 1→2 добавляется явно. Это внутренняя миграция при обычной установке совместимой версии и не сохраняет данные после удаления приложения. JSON-экспорт избранного — отдельный механизм переноса ограниченного набора записей и не является резервной копией настроек.
