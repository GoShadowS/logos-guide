# Отчёты по задачам

- Создавай отдельный Markdown-файл на каждую завершённую задачу, включая аудит без кода: `YYYY-MM-DD-краткий-slug.md`. Дата в имени и поле «Дата аудита» — фактический день работы; даты Git/GitHub, коммитов, публикации и merge указывай отдельно, не переписывая под них историческую дату отчёта.
- После добавления отчёта обновляй `INDEX.md`, который ведётся от старых записей к новым. Каждый PR указывай с фактическими статусом, head/merge SHA, review и CI. Если PR не создан/не слит, прямо так и напиши; не придумывай merge SHA и не называй рабочую копию опубликованным PR.
- Для версии приложения различай пользовательский план, фактические Gradle `versionName`/`versionCode`, содержимое доступного APK и опубликованный GitHub Release. Планируемую версию не называй собранной/выпущенной без артефакта; отмечай расхождения между Gradle, workflow, тегами и Releases.
- Для установки/перехода записывай обязательные пользовательские действия, проверенную доступность экспорта/импорта, поля резервной копии, данные вне экспорта и риск удаления локальных данных. Не обещай Android Backup, совместимость APK или миграцию на устройстве без проверки.
- При аудите updater-а различай автоматическую проверку, загрузку после действия пользователя и системную установку. Указывай источник, интервал, способ сравнения версий, обработку ошибок, проверку `versionCode`/package/signature и ограничения тестов по исходникам. Release workflow не является доказательством клиентского поведения.
- Для исторических отчётов сохраняй исходные даты, статусы PR и результаты CI. Если данные устарели, добавь отдельный блок с датой текущей сверки; не переписывай прошлое так, будто оно относилось к новому релизу или текущему diff.
- В отчёте указывай цель и результаты; файлы изменений; точные команды/итоги проверок; недоступные проверки с причиной; статус визуального/runtime-тестирования; полный Markdown-инвентарь, если его требует задача; оставшиеся проблемы, PR и точную инструкцию отката.
- Пиши для человека: фиксируй итоги, а не копируй сырые логи. Не сохраняй ключи, пароли, токены, подписи, дампы устройств или иные секретные/чувствительные данные. Не включай сторонние, кэшированные или автоматически сгенерированные Markdown-файлы в проектный инвентарь.
